KP’s ruling this board is built on

“checkout is using stripe, why would we duplicate the data capture?”

KP ⚛ 2026-08-24, verbatim — RULED, and it withdrew the conductor’s own default. There is no ledger row. Stripe holds the payment; the webhook completes the exchanges row that already exists; the split flows downstream from it, as the schema already said. Checkout captures nothing twice.

The ground agrees, and it is worth reading as a single fact: the POST route inserts one row (checkout/route.ts:95–108, eight columns) and the webhook performs one UPDATE on that same row (webhook/stripe/route.ts:45–55, four columns) and inserts nothing at all. The duplication KP refused was already removed once, and its own header says so: “the old flow inserted a second sales record here, duplicating every purchase”.

The delivery, in the plainest shape the ground allows

KP ⚛ ruled: a file_registry row per body into the bucket KP will create. So the delivery adds one step and no tables:

StepWhat it is
1The exchange completes — the webhook sets status: completed. This already happens.
2The success page asks the session route for what was kept. This already happens: kept: {kind, id, name} (session/[id]/route.ts:57 :86).
3NEW — that same route also returns the bodies: the file_registry rows where related_table = 'wares' and related_id = kept.id, each with a signed URL minted on the ask.
4NEW — the same ask, from the stall, for a work already in the vessel’s keeping. One road, two doors onto it.

The URL rides the spot the plan named. kept is already the place the success page looks; the bodies join it there rather than arriving by a second route. No new table, no new column on wares, no schema change — related_table + related_id is untyped by design and file_registry is already generated, validated, routed, and entirely uncalled. This is a door someone already built.

Minted, never stored. file_registry.access_token stays null. A stored link is a credential sitting in a row; a minted one is an answer to a question asked by someone the base has just checked.

Two findings, and the second is the important one

The split shown is not guaranteed to be the split charged. PriceBreakdown renders at the stall against ware.price (CreationDetail.tsx:128–132). The gesture then posts, the server calls calculate_sovereign_price, and useCheckout.tsx sends the vessel straight to Stripe with whatever came back (:55–59, a hard window.location.href). Where the acid test moves the number, the vessel reads one price, presses a button, and meets another — with no screen in between. Law 7 says the buyer sees the split at the moment of purchase. Drawn: the one confirming screen, fired only on a change.

Three defaults for one number, and they disagree. PriceBreakdown.tsx:22 defaults residualPoolPercent = 50; the Loom defaults 30 (StudioCreate.tsx:84); the checkout route writes '30' into Stripe metadata (route.ts:137). Any surface that renders the breakdown without passing the prop tells a vessel 50%. The standing default is 0 — a pledge nobody has made (residual-system.md, KP ⚛ 2026-08-24) — and none of the three live values is it. Drawn with no component default at all: the number is the ware’s or it is not shown.

One value written and read by nobody. residualPoolPercent goes into Stripe metadata (route.ts:137) and no code anywhere reads it back. Either it is the residual’s provenance at the moment of exchange — in which case it belongs on the row, not in the processor’s metadata — or it is nothing. Named for the spec; not decided here.

Two wiring notes for the spec — reported, not designed

The webhook’s completed branch matches on stripe_session_id alone (webhook/stripe/route.ts:45–55), with no .eq('status', 'pending') guard — unlike its own failure branch, which has one (:79–80). A replayed event rewrites a completed row. It matters more once a delivery hangs off that status.

The session route’s ownership check runs only if an exchange row is found (session/[id]/route.ts:44–49); with no row it falls through and returns the Stripe session anyway. Today that leaks a session’s shape. Once the delivery rides this route, the guard has to be the first thing it does.

The sensory ten, here

pace control — the success page polls every 2s and stops itself the moment the state settles (CheckoutForm.tsx:111–116). No timer is shown to the vessel; the waiting state says “this can take a moment” and offers Look again. Nothing counts down.

progress saving — an unauthenticated gesture stashes the intent and replays it once after the door (useCheckout.tsx:34–38 :71–97), so signing in does not cost the vessel their place. And the delivery is not a one-shot: the bodies are re-askable from the stall forever, which is the deepest form of this point on this board.

no flashing · no autoplay — a spinner and nothing else.

plain language — three rewrites below. The success and error copy is already the best-written in the realm and is kept whole.

obvious next steps — every state ends with a way onward, including the failed one. The delivery adds three plainly-labelled ones and nothing else competing.

more-info door — the split is on the page, not behind a link; every line says where that money goes — of the 10% fee, 70% to the machine and 30% to the residual pool; then the pledged share of the profit to that same pool, and the rest divided equally among this ware’s contributors.

reduced motion — the spinner is the only motion and it is a status indicator, not decoration.

contrast — on surface: heading starDust 12.3:1, body /70 6.7:1, filenames /60 5.3:1, artisan earnings sanctuary.green 6.4:1, the success ring 6.4:1. One measurement worth reading twice: the home wash is the alchemist gradient, and its far stop is mystical.albedo #E0E0E0 — the same colour as the text. At the ambient 0.3 the ground becomes #4C4E58 and starDust reads 6.3:1. At full strength it reads 1.0:1 and the page is blank. This one room is where the 0.3 law is not a preference.

keyboard — each body’s Take it is a real control naming its own file to a screen reader, not a bare icon; the state cards already carry role="status" where they announce a change (:225 :230).
