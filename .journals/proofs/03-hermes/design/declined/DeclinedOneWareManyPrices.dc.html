✕ Declined — one ware carrying several prices

One wares row for the tiers, with the rungs held inside it. The shape every pricing page implies.

What it looked like

Standing at this loom

one row · price: null · metadata.rungs: [ … five of them … ]

🕯️ Supporter $10.00 / mo
🛡️ Guardian $25.00 / mo
🌿 Steward $50.00 / mo
🔮 Visionary $100.00 / mo
👑 Sovereign $250.00 / mo
Stand with it — $10.00 each month

The case for it, honestly

It is one thing at the stall, which is what a vessel actually experiences — nobody stands in a bazaar thinking “these are three products”. It keeps the Loom to one form instead of three near-identical ones, keeps one slug and one description in one place, and makes changing the ladder a single edit instead of three that can fall out of step. It also means a rung can be renamed without breaking a link somebody saved. That last one is a real virtue and it is why this was drawn at all.

The ground that declined it

The base has no column for it. wares.price is one nullable number and pricing_model one enum (database.types.ts:6561–6562). Several prices on one row can only live in metadata, which is Json | null — untyped, unvalidated, unconstrained. That puts money in the one column the base cannot check.

And the split code would have to read it there. The whole model — the 10% fee, its own 30/70, the ware’s pledge, the equal division — runs off columns the base understands. A price the base cannot see is a price the ledger cannot prove, and a public ledger is the thing this house offers instead of a promise.

The pledge is per row, and it is a per-row decision. wares.residual_pool_percent belongs to the ware. Five rungs on one row can carry exactly one pledge between them. Today that is harmless — KP’s is 50 on all of them — but it forecloses a choice the model deliberately leaves to the artisan, on the one ware where the artisan is the person writing the model.

Beneath the schema, the reason it is right. A rung is not a body. KP’s ruling of the same day — one works row + one wares row per app carrying all its bodies — is about the same offer reaching a person three ways. A rung is a different offer at a different price, and the base already has a word for that: another ware. Stretching the bodies ruling to cover prices would be reading it as “one row per thing a vessel might click”, which is not what it says.

What was kept from it

The stall. Five rows, one ladder — board ② draws the rungs together on one page, under one name and one description, because the vessel's experience of a ladder should not be dictated by how many rows hold it. The base's shape is the base's business.

The rungs themselves were ruled after this board was drawn and it did not change the verdict: KP ⚛ 2026-08-24 carried the whole donate set over — Supporter $10 🕯️ · Guardian $25 🛡️ · Steward $50 🌿 · Visionary $100 🔮 · Sovereign $250 👑 (DonationTiers.tsx:15–21). Five rungs make the case for one row stronger in a designer's terms and weaker in the base's: five prices in an untyped metadata blob is five prices the ledger cannot prove instead of three.

Its refusal also surfaced the schema gap that board ⑥ now carries. Trying to write the tiers as one row is what made it plain that pricing_model has no recurring value at all (database.types.ts:6876) — one row or three, the base cannot yet say “every month”, and that is a draft for KP's hand rather than a design decision.
