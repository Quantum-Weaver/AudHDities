# What I learned of myself, reading (hermes) - 2026-08-24

*For the next Sonnet who opens this realm. Honest, unpadded.*

The task had a hard byte ceiling (4,500 bytes) and I badly
underestimated how much my first draft would overshoot it - I wrote
a genuinely good, well-cited brief and it came in at 7,207 bytes,
60% over. Trimming it down took nine separate edit passes, each one
cutting maybe 100-300 bytes, because I kept doing what felt like a
big cut and getting back a 40-byte saving. Rewording a sentence to
sound tighter is not the same as making it shorter, and I conflated
those for longer than I should have. The thing that actually worked
was cutting *content* - dropping a citation, dropping a word like
"already" or "today" that wasn't load-bearing, shortening a quoted
column list to the two or three columns that mattered for the
argument. If I'd measured the gap honestly at the start (2,700 bytes
over) and made one aggressive full rewrite instead of nine incremental
trims, I'd have spent far less of the sitting on arithmetic.

I also caught myself, partway through, about to cite a table's full
~24-column list verbatim to prove I'd actually checked it rather than
guessed. That instinct - show the receipt - is good and I'd keep it,
but it cost real bytes I didn't have. The better move, which I found
eventually, was to name the two or three near-miss columns
(media_urls, cover_url, shipping_info) and just assert "neither table
holds a file pointer" - the specificity of the near-misses does the
proving work without the padding of the full list.

The research phase itself went well and I'd trust the same approach
again: read the plan and digests first for what's already ruled, then
the realm's own bus and README (which for hermes were current and
accurate - not every realm will be this lucky), then go straight to
the checkout API routes and the generated type files rather than
inferring behavior from component names. The single most useful thing
I did was grep for "webhook" across the whole app instead of assuming
the README's checkout diagram was live code - it was accurate, but I
wouldn't have known that without reading the actual webhook handler
and noticing what it doesn't do (no ledger write, no file delivery).
Checking the enum values in database.types.ts directly, instead of
trusting a hook file's type alias, is what surfaced that `work_type`
has no "app" value - a small fact but one that shapes a real question
in the brief.

One thing to watch for next time: I have both a Bash tool and
dedicated Read/Grep tools, and the environment reminder pushes toward
Bash for everything. I used Read and Grep directly for most of this
task because they're simply better suited to reading source files and
searching a large tree - I'd make the same choice again. The byte
counting (`wc -c`) is the one place Bash was clearly the right tool.
